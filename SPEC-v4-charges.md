## 1. Протокол (обов'язковий для кожного кроку)

Порушення цього протоколу знецінює результат — саме через нього буде видно,
що змінив конкретно цей крок, а що є міжseed'овим шумом.

1. **Один крок = один прапорець** у `FEATURE_DEFAULTS`. Нічого не робити «заразом».
2. **RNG-дисципліна.** З вимкненим прапорцем кількість і порядок звертань до
   `sim.rng` мають лишитись незмінними — інакше вимкнений крок мовчки зсуває
   світ. Перевірка: `run-headless` без прапорців має збігтися з
   `data/step0-baseline.json` до цифри.
3. **Регресія перед прогоном:** `node.cmd scripts\verify-determinism.js 300` —
   усі 4 тести. Тест D (Observer знеструмлено → фізика побітово та сама) —
   найважливіший, він і є гарантією розділу 0.
4. **A/B прогін:** `--ticks=3000 --seeds=1..8`, ярлик `stepN-<назва>`,
   далі `compare.js` проти попереднього кроку.
5. **Читати парний знак, а не середні.** Міжseed'ова дисперсія тут більша за
   будь-який очікуваний ефект (популяція по seed'ах: 17…98). Сигнал у
   популяційних метриках — це 7↑/1↓, а не «середнє зросло на 3».
   Розподіл дій — навпаки, агрегат по мільйонах взаємодій, там надійні й
   десяті частки відсотка.
6. **Checkpoint.** Кожне нове поле стану (заряд гена, режим ребра, EMA потоку)
   має потрапити в `checkpoint()` і піднятися у `fromCheckpoint()`, інакше
   тест C розвалиться. Кеші — навпаки, **не** серіалізувати, а перебудовувати.

## 2. Крок 2 — коливання середовища

Прапорець `envOscillation`.

У `Environment.step()` рівень ресурсу зараз стаціонарний: плями рухаються,
але глобальний фон фіксований (`target = 0.15 + Σ плям`).

Додати повільне глобальне коливання з періодом **значно довшим за час життя
частинки** (характерне життя — сотні тіків, отже період 8000–20000 тіків):

```js
const ENV_OSC_PERIOD = 12000;   // тіків
const ENV_OSC_AMP    = 0.5;     // 0 = вимкнено, 1 = від нуля до подвоєння

// у Environment.step(), якщо features.envOscillation:
const osc = 1 + ENV_OSC_AMP * Math.sin(2*Math.PI * this.tick / ENV_OSC_PERIOD);
// множник застосувати до амплітуди плям І до базового фону:
let target = 0.15*osc;
for(const s of this.spots) target += s.strength*osc*Math.exp(...);
```

`Environment` зараз не знає про тік — передати його параметром
`step(tickCount)` або тримати власний лічильник (і серіалізувати).

Жодного RNG. Обґрунтування — термодинамічне циклювання: система періодично
проходить через стани високої концентрації та розсіювання.

**Критерій:** популяція має почати коливатися у протифазі/з лагом до ресурсу.
Якщо ефекту нема — період завеликий відносно тривалості прогону; прогнати
30000 тіків, перш ніж робити висновок.

## 3. Крок 3 — `absorb` між зв'язаними

Прапорець `absorbBondFix`. Це виправлення бага, не балансування.

Зараз `applyOutcome case 'absorb'` не перевіряє наявність ребра. Зв'язана
пара поглинає одне одного, а `bondPhase` наступного тіку вирівнює енергію
назад через `BOND_FLOW_RATE`. Чистий підсумок циклу — мінус 20% на кожен
`absorb` (`transfer*0.8`), тобто комплекс повільно з'їдає сам себе без
зовнішньої причини. При частці `absorb` ≈ 6.5% це помітний тік енергії.

Два допустимі варіанти — **реалізувати обидва за прапорцем-підваріантом і
порівняти**, вони дають різну фізику:

- **(a) заборона:** якщо між `a` і `b` є ребро — `break` (взаємодія
  вироджується в `none`);
- **(b) розрив:** `absorb` спершу рве ребро, потім поглинає — тобто
  поглинання є актом розриву зв'язку.

Рекомендація: почати з (a) як мінімальної зміни, (b) прогнати як окремий
ярлик. (b) цікавіша тим, що дає комплексам механізм розпаду «зсередини»,
але вона ж сильніше б'є по стабільності структур — а це те, що кроки 4–8
намагаються збудувати.

**Увага на RNG:** гілка `absorb` споживає 1–2 звертання до `sim.rng`
(`aWins`, і умовно другий на обнулення). Раннє `break` до цих звертань
зсуває потік. Щоб вимкнений прапорець лишався побітово сумісним, перевірку
ребра ставити **всередині** гілки так, щоб кількість звертань не змінилась,
або свідомо прийняти зсув і зафіксувати це в ярлику прогону.

## 4. Крок 4 — заряди, валентність, насичення

Прапорець `charges`. Найбільший крок; решта спирається на нього.

### 4.1 Представлення

Заряд — ціле 0..5. Кольори `r,g,b` = 0,1,2; антизаряди `r̄,ḡ,b̄` = 3,4,5.

```js
const CHARGE_NAMES = ['r','g','b','R','G','B'];   // великі = анти
const chargeColor = ch => ch % 3;                  // 0,1,2
const chargeSign  = ch => ch < 3 ? 1 : -1;
```

Одне мале ціле — щоб checkpoint лишався компактним і стабільним.

### 4.2 Ген

`{type, value}` → `{type, value, charge}`.

Заряд **не пов'язаний з типом**. Будь-який тип може мати будь-який заряд:
36 комбінацій. `BASE_WEIGHTS` не чіпати й у жодному вигляді не індексувати
зарядом. Якщо кореляція функції й заряду виникне — це має бути результатом
відбору, а не закладеною відповідністю.

Зачепити треба **всі** місця, що конструюють ген:
`Genome.random`, `Genome.recombine` (fallback-гілка), `Genome.mutate`
(вставка, дублювання, збереження при точковій мутації), `clone`,
`checkpoint`/`fromCheckpoint`.

### 4.3 Мутація заряду

Окрема операція з власною ймовірністю, незалежна від мутації значення і типу:

```js
MUTATION.chargeMutRate = 0.03   // стартове значення, сканувати 0.01 … 0.08
```

У `mutate()`, поряд із `typeChangeRate` і `pointRate`:

```js
if(rng.random() < MUTATION.chargeMutRate) charge = Math.floor(rng.random()*6);
```

Новий ген при вставці отримує випадковий заряд. При рекомбінації заряд
успадковується разом із геном — **жодної нормалізації, корекції чи
«полагодження» суми**. Непогашений заряд — це не помилка, це валентність.

### 4.4 Алгебра нейтральності

Це серце кроку. Нейтральність **не вимагається від частинки** — при довжині
геному 6–9 нейтральних випадкових геномів лише 3–4%, і вимога зробила б ~96%
мутацій летальними.

```js
function netCharge(genes){                  // → [nr, ng, nb]
  const n = [0,0,0];
  for(const g of genes) n[chargeColor(g.charge)] += chargeSign(g.charge);
  return n;
}

// відхилення від нейтральної прямої (1,1,1)·t
function chargeResidual(n){
  const m = (n[0]+n[1]+n[2])/3;
  return [n[0]-m, n[1]-m, n[2]-m];
}

function valence(n){
  const d = chargeResidual(n);
  return Math.hypot(d[0], d[1], d[2]);
}
```

`valence === 0` ⟺ `nr === ng === nb`. З цього **самі собою** випливають обидва
способи нейтральності, яких вимагає §2:

- `r + r̄` → `(0,0,0)` → нейтрально;
- `r + g + b` → `(1,1,1)` → середнє 1, відхилення нульове → нейтрально;
- так само `2r+2g+2b`, `r̄+ḡ+b̄` тощо.

Дозволені розміри комплексів **ніде не перелічуються** — вони наслідок цієї
формули.

### 4.5 Погашення через ребро (механізм насичення)

Без цього валентність вузла ніколи не зменшується, і він плодив би зв'язки
нескінченно. Тому крок 4 уже містить міжчастинкове погашення на рівні вузла:

```
residualValence(x) = валентність x після взаємного погашення
                     з безпосередніми сусідами по ребру
```

Алгоритм (детермінований, без RNG):

1. Порахувати `net(x)` і `d(x) = chargeResidual(net(x))`.
2. Сусідів обходити у порядку **зростання id ребра** — не в порядку `Set`,
   інакше детермінізм залежатиме від історії вставок.
3. Для кожного сусіда `y`: взаємно погасити протилежні компоненти
   `d(x)` і `d(y)` (покомпонентний мінімум за модулем із протилежними
   знаками), зменшивши обидва.
4. Те, що лишилось, — `residualValence(x)`.

Кешувати в `entity._residualCache`, інвалідувати в `addBondBetween` і
`removeBond` для обох кінців **та всіх їхніх сусідів** (бо погашення сусіда
змінюється теж). Не перераховувати щотіку.

### 4.6 Насичення як причина зупинки росту

Ніякого правила «комплекс більший за N не росте». Замість нього — у
`applyOutcome case 'stableBond'`:

```js
if(sim.features.charges){
  if(residualValence(a) < VALENCE_EPS || residualValence(b) < VALENCE_EPS) break;
}
```

Насичений вузол не утворює нового зв'язку не тому, що це заборонено, а тому
що **гасити нічого**. `VALENCE_EPS ≈ 1e-6`.

На кроці 6 цей явний гейт стане значною мірою зайвим (насичений вузол нічого
не експресує → не тягне до `stableBond` сам собою). Тоді його треба
**прогнати A/B з гейтом і без** і лишити емерджентний варіант, якщо він
тримає розподіл.

### 4.7 Серіалізація

- `checkpoint()`: `genes: [{type, value, charge}]`;
- `fromCheckpoint()`: підняти `charge`, кеші **не** піднімати — перебудувати;
- `Genome.signature()` (йде в `lineage`): заряд **не** додавати, щоб метрика
  «генетичних ліній» лишилась порівнюваною з базою; за потреби завести
  окремий `chargeSignature()` для Observer'а.

### 4.8 Критерій приймання (§11, у виправленому формулюванні)

Специфікація каже перевірити «піки на 2 і 3 та їхніх комбінаціях». **Цей
критерій у буквальному вигляді непридатний**: кожне ціле ≥ 2 є сумою двійок
і трійок (2,3,4=2+2,5=2+3,6,7…), тож «комбінації 2 і 3» — це просто «всі
розміри ≥ 2», і тест нічого не розрізняє.

Робочий критерій замість нього:

1. **Часово-агреговану** гістограму розмірів компонент (зараз у
   `run-headless.js` знімок лише останнього тіку — це замало; збирати кожні
   `RECORD_INTERVAL` тіків на останній третині прогону).
2. Контроль — ті самі seed'и з `charges:false`.
3. Сигнал: поява **локального максимуму при розмірі ≥ 2** у ≥6 з 8 seed'ів,
   тоді як контроль монотонно спадає. Плюс обмеженість максимального розміру.

Якщо розподіл лишився гладким і монотонним — механізм насичення не працює,
і причину треба шукати **до** будь-яких інших змін (кроки 5–8 не запускати).

## 5. Крок 5 — два режими ребра

Прапорець `edgeModes`.

Для кожного ребра визначається, чи є між кінцями комплементарні заряди.
Критерій — алгебраїчний, **не таблиця пар**:

```js
const dot = d_a[0]*d_b[0] + d_a[1]*d_b[1] + d_a[2]*d_b[2];
// dot < 0  → режим А (анігіляція): заряди взаємно гасяться
// dot >= 0 → режим Б (домінування)
```

**Режим А — провідність.** Потік у `bondPhase` як зараз (`BOND_FLOW_RATE`).

**Режим Б — домінування.** Перетік різко знижений:
`BOND_FLOW_RATE * BOND_FLOW_DOMINATED`, старт `0.1`, сканувати `0 … 0.3`.
Натомість заряди вступають у **циклічне** домінування:

```
r ≻ g ≻ b ≻ r        і симетрично для антизарядів
domColor(x) = argmax |d(x)[i]|,  нічия → менший індекс (детермінізм)
aDominates  = (domColor(a) + 1) % 3 === domColor(b)
```

Циклічність обов'язкова. Лінійна ієрархія (`r > g > b`) схлопнула б популяцію
до одного заряду; цикл симетричний щодо повороту, жоден заряд не привілейований,
і це відомий механізм підтримки різноманіття в просторових системах.

Ген домінуючого заряду експресується, підлеглого — приглушується (сила
приглушення — крок 6, параметр `DOMINATION_SUPPRESS`).

Зберігати `bond.mode` і `bond.dominator` (id вузла або `null`), перераховувати
при створенні ребра і при інвалідації кешу зарядів; серіалізувати.

**Наслідок, який має виникнути сам і якого не треба програмувати:** топологія
енергетичних потоків перестає збігатися з топологією зв'язків — усередині
одного комплексу з'являються провідні ділянки й ізолятори.

## 6. Крок 6 — експресія за зарядом

Прапорець `chargeExpression`. Тут `outcomeVector` перестає бути функцією
всього геному.

### 6.1 Які гени мовчать

Погашення з §4.5 піднімається з рівня вузла на рівень **окремого гена**.
Детерміновано, у порядку геному:

1. **Пари всередині частинки:** для кожного кольору `c` спарувати звичайні
   гени кольору `c` з анти-генами того ж кольору в порядку появи — обидва
   члени пари мовчать (як спарені електрони).
2. **Трійки всередині частинки:** серед решти брати по одному кожного кольору
   (окремо для звичайних, окремо для анти) — трійка мовчить.
3. **Через ребро:** решту погасити проти непогашених генів сусідів, обходячи
   ребра за зростанням id.
4. Те, що лишилось непогашеним, — носії валентності, вони й експресуються.

Інваріант, який варто перевірити тестом: кількість непогашених генів > 0
тоді й лише тоді, коли `valence > 0`. Дві формули мають узгоджуватись.

### 6.2 Вектор

```js
weight_i = 1                      // непогашений і не приглушений
         | DOMINATION_SUPPRESS    // приглушений домінуванням (крок 5)
         | silentWeight           // погашений
```

**Нормування лишити на повній довжині геному** (`/ Math.sqrt(n_total)`, не
`n_expressed`). Інакше майже повністю замовклий вузол підсилив би свої
кілька вцілілих генів і став би не інертнішим, а гострішим — це зруйнувало б
увесь сенс насичення.

### 6.3 `internalState` як поріг експресії

Це те, чого вимагає §5: стан має модулювати поріг.

```js
silentWeight = EXPR_SILENT_BASE * (1 + Math.tanh(e.internalState*0.5)) / 2;
// EXPR_SILENT_BASE = 0.3 → діапазон 0 … 0.3
```

Збуджений вузол частково «пробиває» мовчання погашених генів; спокійний
мовчить повністю.

**Рішення, яке треба ухвалити тут:** на кроці 1 `internalState` вже отримав
readout через різкість softmax'у (`beta = 3·(1+tanh(exc·0.5)·0.5)`). Тримати
обидва readout'и — це подвійний рахунок одного й того самого стану.
Рекомендація: на кроці 6 **перенести** readout зі softmax'у в поріг експресії
(β повертається до сталої 3), і прогнати A/B трьох варіантів: лише β,
лише поріг, обидва. §5 описує саме поріг, тож за інших рівних лишати поріг.

### 6.4 Що з цього має вийти саме

Один геном у різних умовах і в різних позиціях комплексу дає різну поведінку.
Вузол у центрі має більше погашених зарядів, ніж вузол на периферії, тому
центр інертніший — **ядро й оболонка без гена «спеціалізація»**. Це і є
перевірка, що механізм працює: заміряти середню частку експресованих генів
як функцію степеня вузла; вона має спадати.

Експресія **не змінює геном**. Геном лишається незмінним за життя і єдиним
каналом спадковості.

## 7. Крок 7 — внесок сусідів (глибина 1)

Прапорець `neighborVector`.

```js
effectiveVector(x) = ownVector(x) + k · Σ ownVector(сусіди по ребру)
```

- **Тільки глибина 1.** Вузол читає свої ребра, не зв'язну компоненту.
  Ітерація до збіжності повернула б глобальне знання про організм.
- **Тільки `outcomeVector`.** Не `energyGain`, не `speed`, не `upkeep` —
  інакше це прямий бонус за складність, тобто програмування результату.
  Зв'язаний вузол має поводитись **інакше, а не краще**.
- `k` — сканувати `0.05 … 0.5`, не вгадувати. Замалий — нічого не зміниться;
  завеликий — власний геном перестане мати значення і спадковість обірветься.

### Найімовірніше місце зламати детермінізм

`phenotype` кешується в конструкторі `Entity`. Ефективний вектор треба
інвалідувати при зміні ребер, а не перераховувати щотіку. Пастка: при
увімкненій експресії зміна ребра `(a,b)` змінює **власні** вектори `a` і `b`
(бо змінюється погашення), а отже — **ефективні** вектори всіх сусідів `a` і `b`.
Тому інвалідувати треба `a`, `b` **і всіх їхніх сусідів**. Шлях смерті вузла
(`deathPhase` → `removeBond`) це покриває, якщо інвалідація живе всередині
`removeBond`, а не поруч із викликами.

**Обов'язковий тест:** реалізувати повільний еталонний шлях (усе
перераховується щотіку, без кешу) за debug-прапорцем і порівняти
`checkpoint()` після 500 тіків побітово з кешованою версією. Без цього тесту
крок 7 не приймати.

## 8. Крок 8 — стабільність зв'язку як наслідок

Прапорець `flowBondStability`.

Зараз `BOND_BREAK_PROB = 0.0006` — плоска константа для всіх ребер незалежно
від того, що з чим зв'язано. Через це всі комплекси однаково нестабільні за
правилом, і жодна конфігурація не може виділитись як стабільний вид.

У `bondPhase` уже рахується `delta = (a.energy-b.energy)*BOND_FLOW_RATE`.
Накопичувати на ребрі EMA односторонності потоку і виводити ймовірність
розриву з неї:

```js
bond.flowEMA = (1-FLOW_EMA_A)*bond.flowEMA + FLOW_EMA_A*delta;   // A ≈ 0.05
const breakProb = BOND_BREAK_PROB
                * (1 + BREAK_FLOW_K * Math.abs(bond.flowEMA))
                * (1 + BREAK_VALENCE_K * localImbalance);
```

Сильний односторонній перетік напружує зв'язок; збалансований — ні. Таблицю
«які пари стабільні» не складати.

### Розбіжність у специфікації, яку треба вирішити тут

§7 просить зробити менш стабільним **неквантований сумарний заряд комплексу**.
Але §6 прямо забороняє вузлу знати зв'язну компоненту, а сумарний заряд
комплексу — це саме глобальне знання. Дві вимоги суперечать одна одній.

Рішення: брати **локальний проксі** — непогашену валентність двох кінців
ребра (`localImbalance = residualValence(a) + residualValence(b)`). Вузол
із великою непогашеною валентністю всередині зв'язаної структури і є локально
незбалансованим. Це дає потрібну фізику («чим далі від нейтральності, тим
вища ймовірність розпаду» — пор. нестабільні ізотопи: існують, але недовго),
не вводячи глобального знання. Заборони немає — є нестабільність.

`bond.flowEMA` серіалізувати.

## 9. Відкриті питання (§13): стан і рекомендації

### 9.1 Чи зберігається заряд при `construct`

**Тут є пастка, якої немає в тексті специфікації.** Варіант «заряд дитини
походить із зарядів батьків, і батьки щось втрачають» вимагає, щоб батьки
змінили свої гени — а це прямо суперечить інваріанту «геном лишається
незмінним за життя і єдиним каналом спадковості» (§5). Стехіометрію не можна
ввести просто «відніманням у батьків».

Три несуперечливі шляхи:

- **(A) без збереження.** Заряди копіюються разом із генами при рекомбінації,
  батьки не втрачають нічого. `construct` лишається народженням. Просто,
  реакційних циклів не дає.
- **(B) гейт без мутації.** `construct` не відбувається, якщо сумарна
  непогашена валентність батьків не «покриває» валентність дитини. Геноми
  недоторкані, з'являється справжнє обмеження, але не справжня стехіометрія.
- **(C) негеномна поляризація.** Завести окреме **негеномне** поле
  `entity.polarization` (вектор у (r,g,b)), яке приймає дисбаланс і повільно
  розсмоктується. Тоді `construct` справді стає реакцією з законом
  збереження, а геном лишається незмінним. Найскладніше й найцікавіше.

**Рекомендація:** крок 4 робити на (A) — те, що він перевіряє (дискретність
розподілу розмірів), від збереження заряду не залежить. Далі (B) як дешевий
A/B. (C) — окремим кроком 9 після того, як кроки 4–8 дадуть зрозумілу
картину; інакше не буде видно, що саме дало ефект.

### 9.2 Значення `k` — сканувати `0.05 … 0.5`, не вгадувати (крок 7).

### 9.3 Чи гасяться заряди всередині однієї частинки

**Рекомендація: так, і всередині, і між частинками** — інакше довгий геном
із `r` та `r̄` поруч тягав би фіктивну валентність, і насичення втратило б
сенс. Порядок: спершу внутрішньочастинкові пари, потім трійки, потім ребра
(§6.1). Це ж робить «мовчання спарених» природним.

### 9.4 Що робить домінування: повністю чи частково

**Рекомендація: частково**, `DOMINATION_SUPPRESS = 0.25`, сканувати `0 … 0.5`.
Повне приглушення (`0`) робить підлеглий вузол абсолютно інертним, і ребро
режиму Б перетворюється на смертний вирок замість асиметрії.

## 10. Чого не програмувати (жорсткий список)

Не додавати правил, які прямо створюють:

- реплікацію структури, копіювання топології, успадкування ребер;
- дозволені розміри чи форми комплексів;
- таблицю стабільних сполук;
- бонус за складність, розмір, кількість зв'язків чи кооперацію;
- поняття організму, клітини, мембрани, виду, хижака, паразита;
- будь-яку fitness-функцію.

Заряд дає стабільність і дискретність, тобто **передумову** появи повторюваних
типів. Він не гарантує автокаталізу. Насичений комплекс — це стабільна
молекула, а не реплікатор. Замикання циклу має або виникнути, або ні.

**Допустимі результати:** складність не виникає; популяція вимирає; система
коливається між бумом і колапсом; виникають стабільні види без реплікації.
Кожен із них — результат, а не невдача.

## 11. Критерії перевірки (Observer, не фізика)

Зафіксувати **до** прогонів:

- **Тристоронній тест мотиву.** Конфігурація цікава, якщо одночасно:
  (1) живе довше за рандомізований контроль; (2) після її появи підвищується
  ймовірність появи схожої поруч; (3) генетична схожість між такими
  конфігураціями вища за фон.
- **Causal return із розділенням за глибиною.** Сильні ребра (учасник створив
  вузол) і слабкі (учасник вплинув на вузол) — окремо. Глибина 1 тривіальна,
  це пряме розмноження. Цікава область — глибина ≥ 3.
- **Нульова модель.** Журнал подій уже пишеться (`--events`). Перемішувати
  лише приписування функціональних бакетів до елементів у межах вузького
  вікна часу й простору. 100+ перемішувань, z-score.
- **Роздільність бакетів** зафіксувати до прогону і прогнати аналіз на трьох
  роздільностях. Сигнал, що існує лише на одній, — артефакт.
- **Валідність зарядової механіки** — див. §4.8 (у виправленому формулюванні).

Observer не може впливати на фізику. Перевіряється тестом D у
`verify-determinism.js` — побітово.
